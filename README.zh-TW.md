# 跨形體操作（Cross-Embodiment）於 LIBERO

> 英文版見 `README.md`。本文記錄專案目標、目前可運作的部分，以及今晚遇到的問題。

## 這個專案在問什麼

**在一台機器人上訓練出來的策略，能不能驅動另一台機器人？**

LIBERO 是 Franka Panda 的基準測試，而現代 VLA 在上面表現極好——VLA-JEPA（ECCV 2026）就是該領域的頂尖成績。**超越那個分數不是我們的目標，也不可能是我們的貢獻。**我們問的是一個更窄、目前沒有答案的問題：*同一個策略、同一個場景、換一支手臂。*

假設是：策略的**空間意圖**可以遷移，即使它的**運動輸出**不行。因此管線把兩者拆開：

```
RGB + 語言 ──► VLA ──► SE(3) 意圖 ──► 規劃器（URDF、關節極限、
                                      碰撞）──► 關節指令
```

第二個形體是 **UR5e**，跑在 LIBERO 原本的 Panda 場景裡，並裝上 Panda 夾爪，讓同一個姿態在兩支手臂上代表完全相同的意義。

## 已驗證可運作的部分（Panda）

| 階段 | 結果 |
|---|---|
| VLA-JEPA rollout，`libero_object/0` | 4/4 成功 |
| keypose 抽取 | 7 個 keypose、19.1 倍壓縮、幾何保真度 1.04 |
| keypose 重播可重現任務 | 4/4 |
| 深度感知世界（無特權資訊） | 113,918 點 → 3840 個障礙物 |
| cuRobo IK（含完整世界與自碰撞） | **7/7，誤差 0.00 mm** |
| 適用範圍守門 | 接受抓取任務、拒絕抽屜任務 |

**UR5e 也確實打開了抽屜**（影片為證）：同場景、同夾爪、同路徑點，只換執行器。

| 手臂 | 執行器 | 抽屜 |
|---|---|---|
| Panda | OSC（任務空間局部下降） | **141.2 mm — 打開** |
| UR5e | OSC | 0.0 mm — 完全沒碰到 |
| UR5e | IK + 關節控制 | **140.4 mm — 打開** |

其他已量測且成立的事實：

* 兩支手臂的場景完全相同：16 個物體，最大偏移 **0.0000 mm**
* 底座位置與姿態相同、TCP 皆為 **0.0970 m**
* cuRobo 的 FK 與 MuJoCo 相符至 **0.0002 mm**（200 組隨機構型）
* keypose 抽象的邊界：**可抓取（prehensile）任務成立，非抓取任務失敗**。抽屜是用「勾」的方式打開（全程夾爪張開），姿態序列無法編碼「仍然勾著」這件事

## 今晚的問題

把同樣的 7 個 VLA keypose、同樣的深度世界交給 UR5e，得到 **0/7**。

我對原因提出了**七個**假設，每一個都被後續量測推翻：

| # | 假設 | 結果 |
|---|---|---|
| 1 | UR5e 構型上搆不到 | 錯——影片裡它打開了抽屜 |
| 2 | 世界障礙物過期 | 錯——換成即時深度世界無變化 |
| 3 | 抓取姿態必然接觸，被碰撞檢查否決 | 錯——豁免半徑無效 |
| 4 | 體素表面膨脹（半個體素） | 錯——縮小方塊後無變化 |
| 5 | 缺少 `cspace` | 是真的設定缺陷，已修，但不是原因 |
| 6 | 場景 arena 不同、底座未驗證 | 方向正確 |
| 7 | 自碰撞忽略集不完整 | 錯——關閉自碰撞後無變化 |

途中確實找到並修好三個真實錯誤：

1. **`OnTheGroundUR5e` 沒有註冊。** LIBERO 依 **arena** 決定前綴：桌面場景用 `MountedX`，地板場景用 `OnTheGroundX`。`libero_object` 是地板場景，所以 UR5e **根本沒有被建立過**。
2. **底座差 912 mm。** 我讓 `OnTheGroundUR5e` 繼承 `MountedUR5e`，因而沿用了 `RethinkMount` 底座——那是一根 0.912 m 的立柱。Panda 站在地上，UR5e 懸在空中 0.912 m。之前所有 UR5e 數字都是對著這個錯誤量的。
3. **cuRobo 設定缺 `cspace`**、欄位名是 `default_joint_position`（不是 `retract_config`）、`position_limit_clip: 0.1` 會讓 0.04 m 的夾爪關節上下限反轉。

### 目前的關鍵證據

決定性的對照實驗是**固定機器人、只換描述檔**：

```
Panda / NVIDIA 官方 franka.yml     7/7   誤差 0.00 mm
Panda / 我產生的設定檔             0/7   誤差 0.00 mm
```

**所以問題從來不是 Panda vs UR5e，而是「NVIDIA 的描述檔 vs 我產生的描述檔」。** UR5e 之所以看起來有問題，只是因為 cuRobo 沒有內建 UR5e 設定，它永遠只能用我產生的那份。

再往下看求解器的原始輸出：

```
position_error ≈ 1e-8 m      rotation_error ≈ 1e-7      feasible = False
```

解答精確到**奈米等級**，被判定不可行的是 `feasible` 這個旗標。自碰撞已關閉，因此只剩**與世界的碰撞**。而 NVIDIA 的設定在**同一個** 3840 障礙物世界裡是 `feasible = True`。

目前最可能（**尚未證實**）的原因是碰撞球太大：

```
NVIDIA panda_link0 ：2 顆球，半徑 0.03
我的   robot0_link0：5 顆球，半徑 0.072 – 0.114
```

大了 2–4 倍。半徑 0.114、中心在 z=0.059 的球會延伸到 z = −0.055 … 0.173，直接穿進深度相機看到的地板。底座不會移動，所以這個碰撞在**每一個**構型都成立——正好符合「解精確、但永遠不可行、且與姿態無關」的特徵。

## 誠實的結論

* **管線在 Panda 上端到端可運作**，且不使用任何特權資訊。
* **UR5e 沒有任何有效數字**。所有先前的跨形體結論都已撤回。
* 瓶頸是**我自己產生的機器人描述檔**，不是形體遷移本身、不是規劃器、不是感知。

方法論上的教訓，值得寫在最前面：

> **先驗證你正在失敗的那個場景裡的座標框，再談任何機制。**
> 今晚七個假設，每一個都有合理的故事，也都被一次量測推翻。真正有效的做法只有一種——**固定機器人，只改一個產物**，那是使用者提出的對照實驗，不是我提出的。

另一個教訓：**寫在文件裡的陷阱會重複發生，寫成測試的不會。** 因此新增了 `xembody/contract.py`：姿態必須攜帶它所屬的座標框，跨框傳遞會直接拋出例外。它在 0.4 秒內就抓到了那個 912 mm 的錯誤。

## 追加：配對資料與「策略在想什麼」的量測

在確認 Panda 管線可運作、UR5e 卻失敗之後，我們把問題從「規劃器」轉向「策略本身」。

### 即時 rollout（VLA-JEPA 真的在驅動手臂）

| 手臂 | 結果 |
|---|---|
| Panda | **2/2 成功**（134、135 步） |
| UR5e | **0/2**，跑滿 280 步，而且**抓錯物體** |

影片：`videos/vla_live_*.mp4`，疊加了策略的意圖（紅色軌跡＝指令方向、綠/黃條＝夾爪狀態、藍條＝指令強度）。

**抓錯物體**是關鍵線索：那是**意圖**錯誤，不是**執行**錯誤。執行失敗會是「伸向正確物體但抓不起來」。

### 交叉輸入實驗：是影像還是本體感覺？

把兩支手臂放到**同一個 TCP 位姿**，然後交叉餵入影像與狀態：

| 輸入 | 指令方向 | ‖v‖ |
|---|---|---|
| Panda 影像 + Panda 狀態 | `[0.506, −0.839, 0.197]` | 0.262 |
| UR5e 影像 + Panda 狀態 | `[0.388, −0.920, 0.057]` | 0.727 |
| Panda 影像 + UR5e 狀態 | `[0.507, −0.840, 0.196]` | 0.279 |

* 只換**狀態**：`cos = 1.000`——策略**完全忽略本體感覺**。
* 只換**影像**：`cos = 0.980`，方向幾乎不變。

> **重要修正：** 當時我從這一個樣本推論出「幅度被放大 2.8 倍」，並據此提出一整層「幅度校正」。後續在 8 個軌跡階段重測後發現，**幅度比值中位數是 0.95**，2.8 只是 0.80–2.19 分佈裡的一個尾端樣本。**沒有系統性的幅度膨脹。**這個機制是我從 n=1 推論出來的，已撤回。

### 配對資料收集（標註是免費的）

把兩支手臂放到同一個 TCP，各問策略一次，**Panda 的動作就是 UR5e 觀測的監督標籤**——不需要人工標註、不需要獎勵、不需要真實機器人。

`examples/collect_pairs.py`，資料在 `pairs/`。共 **450 組配對**、兩個 suite、多個初始狀態：

| 階段 | libero_object | libero_goal |
|---|---|---|
| 接近 0.0–0.2 | cos +0.998，**0.0%** 不一致 | cos +0.992，**0.0%** |
| 接觸 0.4–0.6 | cos +0.969，**26.4%** | cos +0.981，**27.3%** |
| 末段 0.8–1.0 | cos +0.925，37.0% | cos +0.952，**45.2%** |

**夾爪通道 450 組只有 1 組不一致**——「要不要合爪」這個離散決策幾乎完美遷移，只有連續方向會抖動。

### ~~目前最一致的解釋：手臂自身的遮擋~~ —— **已推翻**

> 這一節原本主張「不同形狀的手臂遮擋物體的方式不同」是失敗主因。**那是錯的**，保留於此作為紀錄。

真正的原因單純得多：**UR5e 從一開始就站錯地方。**

記錄整條 TCP 軌跡後可以看到，UR5e 在**第 5 步**就已經離 Panda **178 mm**，而且之後是震盪（178 → 269 → 189 → 269 → 101），**不是**逐漸偏離。沒有累積、沒有漂移——一開始就在別的地方。

那 178 mm 是幾小時前就量過的數字：

```
Panda 起始 EE  [-0.217,  0.009, 1.171]
UR5e  起始 EE  [-0.324, -0.025, 1.030]     相距 181 mm
```

LIBERO 的每一段示範都從**同一個 home pose** 開始遙操作，所以策略對「從別的位置開始」**完全沒有訓練訊號**。這不是模型過擬合，而是**資料集對初始構型的覆蓋率是零**——任何在 LIBERO 上訓練的策略都會如此。

### 修正後的結果

只加上一行「把手臂 IK 到來源手臂的起始 EE 位姿」：

| 設定 | 結果 |
|---|---|
| Panda | **3/3**（140、134、147 步） |
| UR5e，**有**起始對齊 | **3/3**（124、134、135 步） |
| UR5e，**沒有**起始對齊 | **0/3** |

**閉環的 VLA-JEPA 可以驅動 UR5e 完成任務。**

### 這推翻了什麼

* **外觀 OOD（畫面裡是一支完全不同的手臂）是可以容忍的。**
* **構型 OOD（起始位置差 18 cm）不行。**

我們花了一整晚在遮擋假說上、為它訓練了一個校正器、還把它寫進這份文件當作主要解釋——結果手臂的**外觀**遠不如手臂的**起點**重要。

而且早有旁證被忽略：抽屜實驗中兩支手臂的指令在前 75 步 `cos = 0.999`——那個 harness 有做起始對齊。今晚重寫的版本沒有。同一個策略、同一組手臂，差別只在起點。

* **動作校正器現在反而有害**：對齊後不用校正器是 3/3，用了是 0/1。它修的是對齊已經消除的差異。
* 對真實部署是好消息：真機本來就可以先回 home pose，這是一行前置條件，不是研究問題。

### 對設計的意涵

* 接近與搬運**不需要校正**（0% 不一致）
* 真正要處理的是**接觸窗口**，兩個 suite 都約 26–27%
* 因此校正器應該是**階段/幅度門控**的，而不是全域套用
* 這也和 E1 的結論相符：keypose 抽象正是在**接觸**時失效

### 額外發現

* `libero_goal` 的抽屜任務會在中途**成功並終止**，因此收集配對時會出現
  `ValueError: executing action in terminated episode`——ep2 就是這樣失敗的。

## 最終結果：閉環跨形體遷移

只加上**起始位姿對齊**（把 UR5e IK 到 Panda 的起始 EE 位姿），VLA-JEPA 直接驅動 UR5e：

| suite | 任務 | arena | Panda | UR5e（對齊後） |
|---|---|---|---|---|
| `libero_object/0` | 拿起罐頭放進籃子 | floor | 3/3 | **3/3** |
| `libero_spatial/0` | 拿起黑碗（語言指代） | table | 3/3 | **3/3** |
| `libero_10/0` | 兩個物體放進籃子（長時序） | living room | 3/3 | **3/3** |
| `libero_goal/0` | 打開抽屜（非抓取式） | table | 3/3 | **2/3** |

**總計 11/12**，橫跨三種 arena、四種任務型態、抓取與非抓取、語言指代與長時序。
步數也幾乎一致（例如 `libero_10`：Panda 266/245/244，UR5e 262/243/250）。

影片：`videos/eval_<suite>_<robot>_raw_init<N>_ok.mp4`，
總覽圖 `videos/summary_ur5e_transfer.png`。

### 結論修正

**VLA-JEPA 幾乎原封不動地遷移到 UR5e。** 之前看起來像「形體差異」的問題，實際上是**構型 OOD**（起始位置不同），不是**外觀 OOD**（畫面裡是不同的手臂）。

因此下列全部都**不需要**：規劃器、keypose 抽象、學習式校正器。這也代表本專案原本的論點（「意圖遷移、可行性交給規劃器」）在這個設定下**沒有被證實為必要**——真正的瓶頸在別的地方。

### 一個差點變成假結果的陷阱

`libero_10` 第一次跑出 **3/3**，但那是假的：

* 起始對齊誤差 **800 mm**（我把 `living_room_table` 的偏移直接抄 `table` 的，漏掉 `z = 0.42`）
* 「成功」發生在 **第 1–2 步**——長時序任務不可能兩步完成

**LIBERO 在構型錯誤的場景裡會立刻回報 `done`。** 任何統計成功率的 harness 都需要一個「最短步數」健全性檢查，否則這種假成功會直接變成論文數字。
