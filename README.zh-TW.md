# 跨形體操作（Cross-Embodiment）於 LIBERO

> 英文版見 `README.md`。本文記錄專案目標、目前可運作的部分，以及今晚遇到的問題。

## 這個專案在問什麼

**在一台機器人上訓練出來的策略，能不能驅動另一台機器人？**

LIBERO 是 Franka Panda 的基準測試，而現代 VLA 在上面表現極好——VLA-JEPA（ECCV 2026）就是該領域的頂尖成績。**超越那個分數不是我們的目標，也不可能是我們的貢獻。**我們問的是一個更窄、目前沒有答案的問題：*同一個策略、同一個場景、換一支手臂。*

假設是：策略的**空間意圖**可以遷移，即使它的**運動輸出**不行。因此管線把兩者拆開：

```
RGB + 語言 ──► VLA ──► SE(3) 意圖 ──► 規劃器（URDF、關節極限、
                                      碰撞）──► 關節指令
```

第二個形體是 **UR5e**，跑在 LIBERO 原本的 Panda 場景裡，並裝上 Panda 夾爪，讓同一個姿態在兩支手臂上代表完全相同的意義。

## 已驗證可運作的部分（Panda）

| 階段 | 結果 |
|---|---|
| VLA-JEPA rollout，`libero_object/0` | 4/4 成功 |
| keypose 抽取 | 7 個 keypose、19.1 倍壓縮、幾何保真度 1.04 |
| keypose 重播可重現任務 | 4/4 |
| 深度感知世界（無特權資訊） | 113,918 點 → 3840 個障礙物 |
| cuRobo IK（含完整世界與自碰撞） | **7/7，誤差 0.00 mm** |
| 適用範圍守門 | 接受抓取任務、拒絕抽屜任務 |

**UR5e 也確實打開了抽屜**（影片為證）：同場景、同夾爪、同路徑點，只換執行器。

| 手臂 | 執行器 | 抽屜 |
|---|---|---|
| Panda | OSC（任務空間局部下降） | **141.2 mm — 打開** |
| UR5e | OSC | 0.0 mm — 完全沒碰到 |
| UR5e | IK + 關節控制 | **140.4 mm — 打開** |

其他已量測且成立的事實：

* 兩支手臂的場景完全相同：16 個物體，最大偏移 **0.0000 mm**
* 底座位置與姿態相同、TCP 皆為 **0.0970 m**
* cuRobo 的 FK 與 MuJoCo 相符至 **0.0002 mm**（200 組隨機構型）
* keypose 抽象的邊界：**可抓取（prehensile）任務成立，非抓取任務失敗**。抽屜是用「勾」的方式打開（全程夾爪張開），姿態序列無法編碼「仍然勾著」這件事

## 今晚的問題

把同樣的 7 個 VLA keypose、同樣的深度世界交給 UR5e，得到 **0/7**。

我對原因提出了**七個**假設，每一個都被後續量測推翻：

| # | 假設 | 結果 |
|---|---|---|
| 1 | UR5e 構型上搆不到 | 錯——影片裡它打開了抽屜 |
| 2 | 世界障礙物過期 | 錯——換成即時深度世界無變化 |
| 3 | 抓取姿態必然接觸，被碰撞檢查否決 | 錯——豁免半徑無效 |
| 4 | 體素表面膨脹（半個體素） | 錯——縮小方塊後無變化 |
| 5 | 缺少 `cspace` | 是真的設定缺陷，已修，但不是原因 |
| 6 | 場景 arena 不同、底座未驗證 | 方向正確 |
| 7 | 自碰撞忽略集不完整 | 錯——關閉自碰撞後無變化 |

途中確實找到並修好三個真實錯誤：

1. **`OnTheGroundUR5e` 沒有註冊。** LIBERO 依 **arena** 決定前綴：桌面場景用 `MountedX`，地板場景用 `OnTheGroundX`。`libero_object` 是地板場景，所以 UR5e **根本沒有被建立過**。
2. **底座差 912 mm。** 我讓 `OnTheGroundUR5e` 繼承 `MountedUR5e`，因而沿用了 `RethinkMount` 底座——那是一根 0.912 m 的立柱。Panda 站在地上，UR5e 懸在空中 0.912 m。之前所有 UR5e 數字都是對著這個錯誤量的。
3. **cuRobo 設定缺 `cspace`**、欄位名是 `default_joint_position`（不是 `retract_config`）、`position_limit_clip: 0.1` 會讓 0.04 m 的夾爪關節上下限反轉。

### 目前的關鍵證據

決定性的對照實驗是**固定機器人、只換描述檔**：

```
Panda / NVIDIA 官方 franka.yml     7/7   誤差 0.00 mm
Panda / 我產生的設定檔             0/7   誤差 0.00 mm
```

**所以問題從來不是 Panda vs UR5e，而是「NVIDIA 的描述檔 vs 我產生的描述檔」。** UR5e 之所以看起來有問題，只是因為 cuRobo 沒有內建 UR5e 設定，它永遠只能用我產生的那份。

再往下看求解器的原始輸出：

```
position_error ≈ 1e-8 m      rotation_error ≈ 1e-7      feasible = False
```

解答精確到**奈米等級**，被判定不可行的是 `feasible` 這個旗標。自碰撞已關閉，因此只剩**與世界的碰撞**。而 NVIDIA 的設定在**同一個** 3840 障礙物世界裡是 `feasible = True`。

目前最可能（**尚未證實**）的原因是碰撞球太大：

```
NVIDIA panda_link0 ：2 顆球，半徑 0.03
我的   robot0_link0：5 顆球，半徑 0.072 – 0.114
```

大了 2–4 倍。半徑 0.114、中心在 z=0.059 的球會延伸到 z = −0.055 … 0.173，直接穿進深度相機看到的地板。底座不會移動，所以這個碰撞在**每一個**構型都成立——正好符合「解精確、但永遠不可行、且與姿態無關」的特徵。

## 誠實的結論

* **管線在 Panda 上端到端可運作**，且不使用任何特權資訊。
* **UR5e 沒有任何有效數字**。所有先前的跨形體結論都已撤回。
* 瓶頸是**我自己產生的機器人描述檔**，不是形體遷移本身、不是規劃器、不是感知。

方法論上的教訓，值得寫在最前面：

> **先驗證你正在失敗的那個場景裡的座標框，再談任何機制。**
> 今晚七個假設，每一個都有合理的故事，也都被一次量測推翻。真正有效的做法只有一種——**固定機器人，只改一個產物**，那是使用者提出的對照實驗，不是我提出的。

另一個教訓：**寫在文件裡的陷阱會重複發生，寫成測試的不會。** 因此新增了 `xembody/contract.py`：姿態必須攜帶它所屬的座標框，跨框傳遞會直接拋出例外。它在 0.4 秒內就抓到了那個 912 mm 的錯誤。
